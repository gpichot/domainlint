This guide takes you from nothing to a failing-then-green CI check. You need Node.js 18+ and a TypeScript or JavaScript project, on one of the [supported platforms](#supported-platforms).

<Steps>

1. **Check your layout**

   domainlint treats every direct child of `src/features/` as a **feature**, and that feature's `index.ts` as its **barrel**, the only file other code may import from.

   <FileTree>
   - src/
     - features/
       - billing/
         - **index.ts** public API: import from here
         - internal/
           - tax.ts private
         - invoice.ts private
       - checkout/
         - **index.ts**
         - pay.ts
     - pages/
       - home.tsx can import `@/features/billing`, not its internals
   </FileTree>

   Different folder names? Point domainlint at them with [`featuresDir` and `barrelFiles`](/configuration/).

2. **Run it, without installing anything**

   From your project root:

   <Reveal>
   <Terminal
     title="~/acme-app"
     command="npx domainlint check"
     lines={[
       { text: 'Analyzed 312 files in 148ms', kind: 'dim' },
       { kind: 'blank', text: '' },
       { text: 'src/features/checkout/pay.ts:1:1 ERROR noCrossFeatureDeepImport', kind: 'err' },
       { text: '  Cross-feature deep import not allowed' },
       { text: '    Import:        "@/features/billing/internal/tax"', kind: 'dim' },
       { text: '    Resolves to:   "./src/features/billing/internal/tax.ts"', kind: 'dim' },
       { text: '    Should use:    "./src/features/billing/index.ts"', kind: 'ok' },
       { kind: 'blank', text: '' },
       { text: '✗ Found 1 boundary violation (1 total violation)', kind: 'warn' },
     ]}
   />
   </Reveal>

   domainlint reads your `tsconfig.json`, so aliases like `@/features/...` resolve the same way your compiler resolves them.

3. **Fix a deep import**

   `noCrossFeatureDeepImport` means code reached into another feature's internals. Export what you need from the barrel, then import from the feature root:

   <ImportFix />

   That one `export` line is the point: it makes `computeTax` part of billing's public API on purpose, not by accident.

4. **Fix an import cycle**

   `noImportCycle` lists the modules in the loop:

   ```
   src/features/billing/invoice.ts:2:1 ERROR noImportCycle
     Import cycle detected:
       ./src/features/billing/invoice.ts ->
       ./src/features/billing/tax.ts ->
       ./src/features/billing/invoice.ts
   ```

   The usual fix is to move whatever both files need (types, constants) into a third module that both import, so the arrows point one way. Use `--shortest-cycles` to see the smallest loops first.

5. **Install it and add it to CI**

   <Tabs syncKey="pkg">
     <TabItem label="npm">
       ```sh
       npm install --save-dev domainlint
       ```
     </TabItem>
     <TabItem label="pnpm">
       ```sh
       pnpm add -D domainlint
       ```
     </TabItem>
     <TabItem label="yarn">
       ```sh
       yarn add -D domainlint
       ```
     </TabItem>
   </Tabs>

   domainlint ships its analysis core as a prebuilt native binary, installed automatically for your platform. No Rust toolchain or compiler is needed. See [Supported platforms](#supported-platforms).

   Add a script next to your type check:

   ```json title="package.json" ins={4}
   {
     "scripts": {
       "typecheck": "tsc --noEmit",
       "lint:arch": "domainlint check"
     }
   }
   ```

   Then run it in CI. It exits with `1` when violations are found, so the build fails:

   ```yaml title=".github/workflows/ci.yml" ins={6}
   jobs:
     lint:
       runs-on: ubuntu-latest
       steps:
         # … checkout, setup-node, install
         - run: npm run lint:arch
   ```

</Steps>

## Adopting on an existing codebase

Got hundreds of violations on day one? Don't fix them all at once. Start strict where it's cheap and loosen the rest:

```json title="domainlint.json"
{
  "overrides": {
    "global": {
      "rules": { "cross-feature-imports": "warn" }
    },
    "features": {
      "checkout": {
        "rules": { "cross-feature-imports": "error" }
      }
    }
  }
}
```

Warnings are printed but don't fail the build. Turn features to `error` one at a time as you clean them up. To focus on one feature's violations, use `domainlint check --feature billing`.

<Aside type="tip" title="Using an AI coding agent?">
domainlint ships agent skills for adopting, configuring, and debugging violations. See the [package README](https://github.com/gpichot/domainlint/tree/main/packages/domainlint#readme) for `npx @tanstack/intent install`.
</Aside>

## Exit codes

| Code | Meaning |
|------|---------|
| `0`  | No violations |
| `1`  | Violations found |
| `2`  | Internal error (e.g. unreadable tsconfig) |

## Supported platforms

The parser, module resolver, dependency graph and built-in rules run in a native (Rust) addon. It is published as one small package per platform (`domainlint-binding-<platform>`), declared as an optional dependency of `domainlint`, so your package manager downloads only the one that matches your machine.

| OS | Architectures |
|----|---------------|
| Linux (glibc: Debian, Ubuntu, Fedora, …) | x64, arm64 |
| Linux (musl: Alpine) | x64, arm64 |
| macOS | x64 (Intel), arm64 (Apple Silicon) |
| Windows | x64 |

The addon works with any Node.js 18+ release, with no rebuild when you upgrade Node.

<Aside type="caution" title="Don't skip optional dependencies">
If you install with `--omit=optional`, `--no-optional` or `pnpm install --no-optional`, the native addon is skipped and domainlint stops with `Failed to load the domainlint native addon`, naming the package it expected. Reinstall with optional dependencies enabled. Likewise, when a Docker image or CI cache is built on one OS and reused on another, reinstall `node_modules` on the target platform.
</Aside>

**Unsupported platform** (for example Windows on ARM, FreeBSD or 32-bit systems): no binary is published, so domainlint fails to start with an error naming your platform. You can [build the addon from source](#building-from-source) if Rust supports your target.

### Building from source

Only needed on an unsupported platform, or when working on domainlint itself. Install a stable [Rust toolchain](https://rustup.rs), then in a clone of the repository:

```sh
pnpm install
pnpm --filter domainlint build:native   # writes packages/domainlint/native/
pnpm --filter domainlint build
```

A locally built addon is preferred over the platform package.
